# Agent Factory database

The application database of Agent Factory. Binding sources: [architecture.md](architecture.md) (decisions D1-D17, the
state table) and the task specification section 4. Status: design. Types are PostgreSQL 16. The Temporal database is
separate and not described here.

## Conventions

- Primary keys are `uuid` (v7, generated by the server, so they sort by time). Exceptions: `task_events.seq` and
  `outbox_events.seq` carry a `bigint generated always as identity` next to the uuid, for cursors and relay order.
- Times are `timestamptz`, set by the database (`now()`), never by a client. Enums are PostgreSQL enums or `text` with a
  `check`; a new value is an expand step (see Migrations). JSONB columns have a `check (jsonb_typeof(...) = ...)` and a
  schema validated in `factory/contracts/` before the write.
- Every mutable table has `row_version bigint not null default 1` and `updated_at`. Every foreign key is `on delete
  restrict`: nothing cascades, history is never removed by a parent's removal.
- Secrets never enter any column (`agents.configuration` holds references such as a credential name, never a value).
  A write whose JSON contains a key on the secret-name list is refused by the contract layer.

## Revisions and the version of a row

- **Task row.** `tasks` has two writers: the API (create, archive, soft delete, title and description are never edited:
  a requirement change is a revision) and `PersistTaskEvent` (status, `current_revision`, `workflow_run_id`, `blocked_from`,
  `paused_from`, `pause_requested`, `assigned_agent_id`, `completed_at`). Every update is
  `update ... set row_version = row_version + 1 where id = $1 and row_version = $2`; zero rows is a conflict. The workflow
  writer re-reads and retries once; it never overwrites a newer status. An API client sends the version it read
  (`If-Match`) and gets `409 version_conflict` otherwise.
- **Revision.** A `revise_requirements` decision inserts the new `task_revisions` row in the same transaction as the
  decision (the number is `max + 1` under the task row lock). `tasks.current_revision` moves only when the workflow
  applies the decision. A refused decision leaves its revision row as history. A decision carries the revision number the
  owner saw; one older than `current_revision` is refused (D14 and the architecture's revision rule).
- **Status moves** are checked twice: the workflow validates a move against the transition table, and a trigger on
  `tasks` refuses a status change that is not a row of the table (the table is the test data and a lookup table
  `task_transitions(from_status, to_status)` loaded by a migration). A final state never leaves.
- BLOCKED returns to `blocked_from`; see Contradictions.
- Per-row versions exist on `projects`, `tasks`, `agents`, `workers`, `task_runs`, `routing_rules`, `api_tokens`.
  Immutable tables carry none.

## Immutable rows and soft delete

- Never updated and never deleted by any application account: `task_revisions`, `task_events`, `task_reviews`,
  `task_approvals`, `run_checks`, `audit_log`, `execution_policies` (a change is a new version row), `task_dependencies`
  (except the removal mark), `task_artifacts` after `confirmed`, and the content of `task_decisions`. A trigger raises on
  `update` or `delete` of the immutable columns, so the rule holds even for a mistake in code.
- Soft delete (`deleted_at`) exists on `projects`, `tasks`, `agents`: the owner marks a row; every list hides it unless
  asked; unique names apply to live rows only (partial unique indexes). A task can be soft deleted only in a final state;
  a project only when archived and with no active task. Rows with history (`task_runs`, `workers`, events) are never
  deleted: `workers` are `disabled`, `api_tokens` are revoked.
- Hard deletion exists only for retention (below) and only through the retention procedure.

## Retention columns

`retain_until timestamptz null` (null keeps the row) on `task_artifacts`, `outbox_events` (done rows),
`idempotency_keys`, `notifications`, `audit_log`. The architecture leaves log retention to its phase, so no value or
default is set here; the owner's choice is in Open for the owner. A purge never touches a row of an open task, a row that
a later row references, or an artifact of a task awaiting approval. `task_events` has no `retain_until`: see Open.

## Dependency cycles

Adding an edge runs in one transaction under `pg_advisory_xact_lock(hashtext('af-deps'))` (edge changes are rare, so one
lock is enough): a recursive query walks `depends_on_task_id` from the new target over live edges and refuses with
`409 dependency_cycle` (the path in the error) if it reaches `task_id`; the self-loop `check` covers the trivial case. A
constraint trigger on insert repeats the walk as a backstop. A removed edge frees the cycle. Dependencies are resolved
anew whenever a BLOCKED task returns to READY (architecture), and `ResolveDependencies` reads only live edges.

## Child tasks

`origin_type` enum: `owner`, `decomposition`, `agent_proposal`, `rework`; `origin_task_id`, `origin_run_id`
(required unless `owner`), `origin_actor`. `depth int not null`, with `check ((parent_task_id is null) = (depth = 0))`;
a trigger sets `depth = parent.depth + 1` and refuses a value above the limit read from the project's policy
(`max_child_depth`). A count limit per parent comes from the same policy. A child may point to a parent only in its own
project. An `origin_run_id` must belong to the `origin_task_id`.

## Run roles and independence

`task_runs.role` fixes who did what. Rules held in the database, not in a prompt: a `task_approvals` row requires an
actor of type owner (agents have no token that can decide); a `task_reviews` row requires a `run_id` of role `reviewer`,
and its `reviewer_id` must differ from the `agent_id` of the `implementer` runs it reviews (agent identity, see Open).
A `reviewer` or `planner` run cannot write a `task_revisions` row (`author_id` is an owner actor).

## Policies, limits and budgets

`execution_policies` is versioned and immutable: `id`; `project_id` nullable (null is the global default);
`version int`, unique with `project_id`; `allowed_commands text[]`; `allowed_directories text[]`;
`allowed_repositories text[]`; `network jsonb`; `git_operations text[]`; `confirmation_required text[]`;
`allowed_tools text[]`; `max_concurrent_tasks`, `max_tasks_per_agent`, `max_run_seconds`, `max_tokens`, `max_cost`
(`numeric`, with `currency`), `max_auto_fixes`, `max_attempts`, `max_child_depth`, `max_children_per_task`;
`auto_accept_low_risk bool default false`; `created_by`; `created_at`. All limit columns are nullable and without
defaults here (numbers are set in the phase that measures them). A project's effective policy is its latest version,
else the global one; a run records the `policy_id` it started under. A change that loosens a security column
(`allowed_*`, `network`, `git_operations`, `confirmation_required`, `auto_accept_low_risk`) is an owner action and an
`audit_log` row (spec 15.4).

## Notifications

`notifications`: `id`; `event_type` enum (spec 16.2 list); `dedup_key text` (for example `worker_offline:<worker id>`,
`task_blocked:<task id>:<blocked_at>`); `task_id`/`worker_id` nullable; `state` enum (`open`, `resolved`);
`occurrences int`; `first_raised_at`; `last_raised_at`; `delivered_at`; `resolved_at`; `retain_until`. Unique index on
`dedup_key where state = 'open'`: raising an open notice only bumps `occurrences` and `last_raised_at`, so one outage
gives one message. A resolved notice allows a new one. Whether an open notice is repeated later is in Open.

## Accounts and rights

Database accounts (none is a superuser; Temporal's account has no right on this database and the reverse):

| Account | Rights |
|---|---|
| `af_migrator` | Owns the schema; DDL; used only by the migration step, never by a running service |
| `af_api` | `select`; `insert` and `update` on mutable tables; `insert` and `select` only on immutable ones; no `delete` anywhere |
| `af_control` | As `af_api`, plus the outbox lease updates and the projection updates of `tasks` and `task_runs` |
| `af_backup` | `select` on everything (`pg_dump`) |
| `af_retention` | `delete` on the tables with `retain_until` only, through one named procedure; exists only if the owner chooses a purge |

Application accounts (API tokens, in `api_tokens`): `id`; `name`; `role` enum (`owner`, `worker`, `reader`);
`worker_id` FK nullable (a worker token is bound to one machine); `prefix text` unique (shown in lists); `token_hash`
(sha-256 of 32 random bytes; the secret is shown once); `created_by`; `created_at`; `expires_at`; `last_used_at`;
`revoked_at`; `replaces_token_id`; `valid_until` (end of the overlap during rotation); `row_version`. Rights: owner
decides, writes and manages tokens; worker registers, reports, uploads for runs of its own machine and posts proposals;
reader reads. Telegram and the web panel run as owner or reader tokens (see Contradictions).

## Migrations and backup

- Forward-only numbered SQL files in `factory/db/`, applied by a one-shot step with `af_migrator` before the API and
  control worker start, under a session advisory lock, each file in one transaction (a statement that cannot, such as
  `create index concurrently`, has its own file). The applied file name and checksum are recorded; a changed applied
  file stops the step.
- Expand then contract (architecture): a release works with the schema before and after it; a column or value is
  removed one release after nothing reads it. Rolling code back needs no schema rollback. A contracting migration is
  preceded by an automatic backup, and its documented rollback is restore from that backup into a new database.
- A failed migration leaves the previous schema (transaction) and the services unstarted; this is the failure scenario
  "migration error" and its check.
- Backup (spec 18.1): `pg_dump` custom format of the application database, taken with `af_backup`, plus the artifact
  files. Order: artifact files are copied first, then the dump, so every artifact row of the dump has its file (storage
  keys are content-addressed and files are never changed). The Temporal database is dumped separately and restored as a
  pair; the backup records both together with the schema version. A backup is not proof: the restore check loads it into
  a separate environment, runs the migrations to head, checks foreign keys, row counts, artifact checksums, and the
  reconciliation below.
- Reconciliation after a restore (scenario D): a restored database may lag Temporal. Outbox rows that were `done` after
  the backup are unknown, so decisions may be redelivered; this is safe because the Update id is the outbox id and the
  workflow checks `used` from the decision row. `PersistTaskEvent` is idempotent by `(task_id, dedupe_key)`, so the
  workflow replays what the projection lacks. A decision confirmed to an owner after the backup point is lost with it:
  the restore procedure says so and lists the owner's decisions by the Temporal history.

## Open for the owner

1. **Retention of logs, events and artifacts.** The specification wants an immutable event journal and a retention policy;
   they pull apart. Options: (a) events are kept forever, only artifacts, done outbox rows, idempotency keys and
   notifications expire; (b) events are partitioned by month and old partitions are detached to cold storage; (c) events
   expire too, with a purge account. Numbers for each class are the owner's.
2. **Reviewer independence.** Options: (a) reviewer is a different agent row than the implementer (checked above);
   (b) also a different provider; (c) only a different run. (a) is the minimum that fits "agent does not accept its own
   result"; (b) costs availability.
3. **Agent-proposed child tasks.** Options: (a) created in `PLANNING` and kept in `BLOCKED` until the owner agrees;
   (b) start automatically when inside the approved scope and depth. The planner rule (cannot widen scope) needs a
   machine-checkable "inside scope" that the architecture does not define.
4. **Notice repeat.** Options: never repeat while open; repeat once a day while open (interval is a setting).
5. **Cross-project dependencies.** Allowed or only inside one project (the schema above assumes any project may
   depend on another, the child-task rule is per project).
6. **Do acceptance and decision tables merge?** Keep `task_approvals` as a view over decisions of accept, reject and
   request_changes (one table fewer) or as written (spec table kept).

## Contradictions

1. The state table says BLOCKED returns "to the state it left", but the dependency rule says a task BLOCKED by a
   dependency "returns to READY". The schema stores `blocked_from` for the first reading; the second needs a rule that
   the owner's dependency decision overrides it. Needs the owner or the architecture to pick one.
2. Roles `owner`, `worker`, `reader` leave the Telegram client without a role: a button press is an owner decision, but
   the client is not the owner's own process. Needs a fourth role or a rule that the hub holds an owner token.
3. The specification calls `task_events` immutable and also asks for log retention; the architecture defers numbers but
   not the conflict (Open 1).
