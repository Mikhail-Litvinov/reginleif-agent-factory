# Agent Factory database

The application database of Agent Factory. Binding sources: [architecture.md](architecture.md) (decisions D1-D31, the
task states, state ownership), [governance.md](governance.md) (the Decision Registry and the regulation, whose tables
are listed below) and the task specification section 4. Status: design. Types are PostgreSQL 16. The
Temporal database is separate and not described here. "Call" marks a design choice made here, open to veto. The schema
is written in Drizzle (D27): the table definitions live in `factory/db/schema/` and are the source of the migrations
(see Migrations and backup); this document is the design the definitions follow.

## Conventions

- Primary keys are `uuid` (v7, generated by the server, so they sort by time). Exceptions: `task_events.seq`,
  `outbox_events.seq` and `audit_log.seq` carry a `bigint generated always as identity` next to the uuid, for cursors and
  relay order.
- Times are `timestamptz`, set by the database (`now()`), never by a client. Enums are PostgreSQL enums or `text` with a
  `check`; a new value is an expand step (see Migrations). JSONB columns have a `check (jsonb_typeof(...) = ...)` and a
  schema validated in `factory/contracts/` before the write.
- Every mutable table has `row_version bigint not null default 1` and `updated_at`. Every foreign key is `on delete
  restrict`: nothing cascades, history is never removed by a parent's removal.
- Secrets never enter any column (`agents.configuration` holds references such as a credential name, never a value).
  A write whose JSON contains a key on the secret-name list is refused by the contract layer.
- Workflow memory names are the camelCase form of the column names (`block_kind` and `blockKind`, `resume_to` and
  `resumeTo`, `pause_requested` and `pauseRequested`).

## The Decision Registry and the regulation

Six tables (34 in all with the 28 above; the four rights tables below make 38), design in [governance.md](governance.md); they hold everything the registry
knows. The registry is off by
default (G1): the tables exist, and nothing in the core reads them. Ids are `uuid` v7; a record also carries a number
from an identity column, shown as `DEC-00042` (the prefix is formatting, not data).

| Table | Columns |
|---|---|
| `regulation_versions` | `id`; `number int` unique (the version number a session sees); `status` enum (`draft`, `active`, `superseded`, `revoked`); `clauses jsonb` (the ordered clauses: each item holds the id of a `rule` record, a trigger checks that it exists, is of kind `rule` and in scope, and makes the rules active with the version, in its transaction); `clauses_bytes int` (checked against `registry.clauseMaxBytes`; a larger draft is refused activation); `basis_version_id` FK nullable (the version it was drafted from); `proposed_by` (actor type and id: an owner or an agent's `registry` token); `conflict_report jsonb` (the result of the check against guards, clauses and active owner decisions at the time of the press); `confirmed_by` FK owners nullable; `confirmation_id` FK nullable (the second press, D23); `created_at`; `activated_at`; `status_changed_at`. Activating a version makes its rules active and the rules it leaves out `superseded`; revoking it revokes its rules, in one transaction. Content (`clauses`, `basis_version_id`, `proposed_by`) is immutable; only the status columns and, once, `conflict_report`, `confirmed_by`, `confirmation_id` and `activated_at` change, and every change is an `audit_log` row. At most one `active` row (partial unique index). Empty until the owner writes the text (G6). |
| `registry_records` | `id`; `number bigint generated always as identity` unique; `kind` enum (`rule`, `decision`, `exception`, `precedent`, `fact`, `permission`); `authority` enum (`owner`, `agent`); `decision`; `exceptions_text`; `grounds`; `consequences`; `reuse` enum (`standing`, `once`); `version int` (starts at 1; a supersede is a new row, never a new version of the row); `question`, `options jsonb`, `pressed_option` (set for a record made from a poll press, word for word; a `fact` and a `precedent` need it); `source` enum (`poll_press`, `owner_button`, `owner_message`, `orchestrator`, `agent_proposal`, `import`); `source_ref text` (press id, inquiry id, or the named file of an import); `run_id` FK nullable; `created_by` (actor type and id); `search_ru`, `search_en` tsvector, generated columns over the text fields (full text, Russian and English configurations); `created_at`; `status_changed_at`; The content columns are immutable. Only `status`, `status_changed_at`, `status_changed_by` and, once, `consumed_at` change, by column grant, and a trigger writes an `audit_log` row for each change and refuses a move that is not in the table of allowed moves (`draft` to `active` or `rejected`; `active` to `superseded` or `revoked`; the rest are final). A `permission` is never one of them and is never made from a poll press (`check (kind <> 'permission' or source = 'owner_button')`). Every other record starts as `draft` and becomes active by the owner's button; a `rule` becomes active only in the transaction that activates its regulation version, never alone. |

text (extension `pg_trgm`); `hnsw (embedding vector_cosine_ops)` on `registry_embeddings`; btree on `(status,
scope_type, project_id, category)` for the filters that run first. The
extensions `pg_trgm` and `vector` are created by the migration under `af_migrator`.

Audit: no table of its own. The status triggers of `registry_records` and `regulation_versions` write `audit_log` rows
(`action` `registry.status` or `regulation.status`, the old and new status and the press or confirmation in `details`, the actor) in the same transaction, so a status change cannot happen unrecorded. Content is never updated; a
change is a new record that `supersedes` the old one (D24). Nothing is deleted.

## Rights tables

Four more tables (38 in all), design in the Rights section of [governance.md](governance.md) (D31). They are not part
of the registry: a chief engineer's grant is never a record and never in the registry search (G16). Not to be confused
with the existing enums: `task_runs.role` (a run's job) and `api_tokens.role` (who may call the API); a role here is a
named list of rights. A run of the chief engineer is a `task_runs` row with the new `role` value `chief_engineer`
(added by the same migration); it never has a `role_assignments` row.

| Table | Columns |
|---|---|
| `roles` | One row per version of a role: `id`; `name text`; `version int`, unique with `name`, contiguous from 1; `status` enum (`draft`, `active`, `superseded`); `rights jsonb` (a list of structured rights, each `action`, `target`, `conditions`; a schema check refuses a malformed one, free text never); `deny jsonb` (the deny rules of the role); `regulation_version_id` FK (the regulation version that holds the role: its contents are part of the regulation, G14); `created_at`; `status_changed_at`. Content is immutable. A row is written with its regulation version and its status follows the status of that version (activation is the two presses of D23 on the version; a role has no route of its own); each change is an `audit_log` row (`action` `role.status`). At most one `active` row per `name` (partial unique index). |
| `role_assignments` | The role of one participant in one task: `id`; `task_id` FK; `participant text` (the plan's name of the participant, stable across attempts); `role_id` FK `roles` (the version in force); `assigned_by` (actor type and id); `created_at`; `superseded_at`. A grant belongs to one participant of one task, not to a run: the next attempt of the same participant finds it, and a run ending does not end it (G17). Indexes: `(task_id, participant)` where `ended_at` is empty on `right_grants` (the check reads it on every call);
`(task_id, request_hash)` on `right_requests` (repeat of a refusal).

## Revisions and the version of a row

- **Task row.** `tasks` has two writers: the API (create, archive, soft delete; title and description are never edited:
  a requirement change is a revision) and `PersistTaskEvent` (status, `current_revision`, `workflow_run_id`,
  `block_kind`, `block_reason`, `resume_to`, `pause_requested`, `stopping`, `end_unconfirmed`, `assigned_agent_id`,
  `completed_at`). Every update is `update ... set row_version = row_version + 1 where id = $1 and row_version = $2`;
  zero rows is a conflict. The workflow writer re-reads and retries once; it never overwrites a newer status. An API
  client sends the version it read (`If-Match`) and gets `409 version_conflict` otherwise.
- **Revision.** A `revise_requirements` decision inserts the new `task_revisions` row in the same transaction as the
  decision (the number is `max + 1` under the task row lock). `tasks.current_revision` moves only when the workflow
  applies the decision. A refused decision leaves its revision row as history. A decision that carries a revision number
  older than `current_revision` is refused `revision_stale` (D14 and the architecture's revision rule).
- **Status moves** are checked twice: the workflow validates a move against the transition table, and a trigger on
  `tasks` refuses a status change that is not a row of the table (the table is the test data and a lookup table
  `task_transitions(from_status, to_status)` loaded by a migration, which includes the cancel, pause and block rows of
  the architecture). A final state never leaves: FAILED too, work goes on in a new task (call, see Child tasks).
- **BLOCKED exit** is decided by `block_kind` (architecture): `scope` to PLANNING; `dependency` to READY; `execution`,
  `usage_limit`, `agent_question` to ASSIGNED; `check_environment` to VERIFYING; `rework_limit` to REWORK_REQUIRED. The
  table `task_transitions` carries these rows and the trigger checks the pair of kind and target.
- Per-row versions exist on `projects`, `tasks`, `agents`, `workers`, `task_runs`, `routing_rules`, `api_tokens`,
  `settings`. Immutable tables carry none.

## Immutable rows and soft delete

- Never updated and never deleted by any application account: `task_revisions`, `task_events`, `task_reviews`,
  `review_finding_outcomes`, `task_approvals`, `run_checks`, `audit_log`, `execution_policies` (a change is a new
  version row), `task_dependencies` (except the removal mark), `task_artifacts` after `confirmed` (except the removal
  mark), `confirmations` (except use), the content of `task_decisions`, the content of `registry_records` and
  `regulation_versions` (their status columns change under audit), `registry_links`, `registry_embeddings`,
  `registry_inquiries` (except the poll columns, set once), `registry_inquiry_results` (except the verdict columns, set once), `roles` (content; status columns change under audit), `role_assignments` (except `superseded_at`), `right_requests` (content; the answer columns are set once) and `right_grants` (except the ending columns, set once). A trigger raises on `update` or `delete` of
  the immutable columns, so the rule holds even for a mistake in code.
- Soft delete (`deleted_at`) exists on `projects`, `tasks`, `agents`: the owner marks a row; every list hides it unless
  asked; unique names apply to live rows only (partial unique indexes). A task can be soft deleted only in a final state;
  a project only when archived and with no active task. Rows with history (`task_runs`, `workers`, events) are never
  deleted: `workers` are `disabled`, `api_tokens` are revoked.
- No row is ever hard deleted (D24). There is no purge account.

## Cleanup on command (D24)

Nothing is deleted by itself, and the history of decisions and events stays for good. The owner's cleanup command for a
task in a final state, and the chief engineer's grant for its part (G15: nothing unsaved), remove only files: the stored logs and artifacts (the `task_artifacts` row stays with its key and
checksum, `upload_state = removed`), the execution folders on the machine and the worktree. It refuses a task that is
not final, an artifact of a task awaiting approval, and a worktree with unpublished changes; the owner may force the
last one (a dangerous operation, two presses). The API records the command as a `task_events` row and an outbox row of
kind `cleanup`. There are no `retain_until` columns. Idempotency keys, done outbox rows, notices and the audit log stay
too (they are small); the backup grows with the history.

## Dependency cycles

Adding an edge runs in one transaction under `pg_advisory_xact_lock(hashtext('af-deps'))` (edge changes are rare, so one
lock is enough): a recursive query walks `depends_on_task_id` from the new target over live edges and refuses with
`409 dependency_cycle` (the path in the error) if it reaches `task_id`; the self-loop `check` covers the trivial case. A
constraint trigger on insert repeats the walk as a backstop. A removed edge frees the cycle. Dependencies are resolved
anew whenever a BLOCKED task returns to READY (architecture), and `ResolveDependencies` reads only live edges.

## Child tasks

`origin_type` enum: `owner`, `decomposition`, `agent_proposal`, `continuation`; `origin_task_id`, `origin_run_id`
(required for `decomposition` and `agent_proposal`), `origin_actor`. `depth int not null`, with `check ((parent_task_id
is null) = (depth = 0))`; a trigger sets `depth = parent.depth + 1` and refuses a value above `max_child_depth`. A
count limit per parent (`max_children_per_task`) comes from the same policy. A child may point to a parent only in its
own project. An `origin_run_id` must belong to the `origin_task_id`.

- **Inside the requirements (D19, call).** A proposal of kind `decomposition` is inside the requirements when every id in
  `covers` exists in the parent's current `acceptance_criteria` and the limits hold: depth, count per parent, and the
  parent's budget (spend is rolled up over a task and its descendants, so a child's spend counts against the root's
  `max_cost` and `max_tokens`). `CreateChildTasks` then creates the child (`origin_type = decomposition`) without the
  owner. Everything else, every `requirement_change` and `suggestion`, is a `task_proposals` row in `open` for the owner;
  accepting it creates a child with `origin_type = agent_proposal`, declining keeps the row.
- **FAILED is final (call).** Work goes on in a new task created by the owner with `origin_type = continuation` and
  `origin_task_id` set to the failed task; nothing is copied, requirements are the owner's.

## Run roles and independence

`task_runs.role` fixes who did what. Rules held in the database, not in a prompt: a `task_approvals` row of type `manual`
requires an owner actor (agents have no token that can decide); a `task_reviews` row requires a `run_id` of role
`reviewer`, and the provider of its `reviewer_id` agent must differ from the provider of the agents of the `implementer`
runs it reviews (D20); a settling run (`disputes_review_id` set) is a fresh run that is not an implementer run of the
task. When no enabled agent of another provider exists the task goes to BLOCKED (`check_environment`). A `reviewer` or
`planner` run cannot write a `task_revisions` row (`author_id` is an owner).

## Migrations and backup

- Drizzle (D27) holds the schema: definitions in `factory/db/schema/` (one file per aggregate), migrations generated by
  `drizzle-kit generate` into `factory/db/migrations/` and then completed by hand in the same numbered file: what
  Drizzle cannot express (triggers, partial and expression indexes where needed, `check` constraints on JSON, grants,
  the rows of `task_transitions`, deferrable constraints) is plain SQL there. Forward only: there is no down file; a
  wrong migration is fixed by a new one. A test regenerates the schema from the definitions and fails when a
  generated part differs from the committed file.
- Applied by a one-shot step with `af_migrator` before the API and control worker start, under a session advisory lock,
  each file in one transaction (a statement that cannot, such as `create index concurrently`, has its own file). The
  applied file name and checksum are recorded; a changed applied file stops the step.
- Creation order. Every foreign key target exists when the key is created, or the key is added by an `alter table` later
  in the same file (or the file that creates the target):

  | Migration | Cycle or forward reference | How it is made safe |
  |---|---|---|
  | 0002 | `tasks.origin_run_id` points to `task_runs` (0004) | the column is created in 0002 without the key; 0004 adds the key after `task_runs` and a trigger that the run belongs to `origin_task_id` |
  | 0003 | `task_decisions.outbox_id` (not null) and `outbox_events.decision_id` | create `outbox_events` without `decision_id`, create `task_decisions` (key to the outbox), then `alter table outbox_events add foreign key (decision_id) ... deferrable initially deferred`; the server makes both uuids first and inserts both rows in one transaction |
  | 0003 | `task_decisions.confirmation_id` and `confirmations.decision_id` | create `confirmations` without `decision_id`, create `task_decisions`, then `alter table confirmations add foreign key (decision_id)`; the first press inserts a confirmation, the decision's insert sets `used_at` and `decision_id` in the same transaction |
  | 0003 | `task_revisions.decision_id` | created after `task_decisions`, no cycle (`tasks.current_revision` is a number, not a key) |
  | 0004 | `workspaces`, `task_runs`, `task_events`, `task_artifacts`, `run_checks` | in this order: runs need `workspaces`, events need runs, checks need artifacts |
  | 0006 | the registry tables (`regulation_versions`, `registry_records`, `registry_links`, `registry_embeddings`, `registry_inquiries`, `registry_inquiry_results`; extensions `pg_trgm` and `vector`) point to `projects`, `owners`, `task_runs`, `api_tokens`; `task_runs.regulation_version_id` and `regulation_seen_id` point to `regulation_versions` | all targets exist since 0001 to 0004; `regulation_versions` is created first, then the two columns are added to `task_runs` by an `alter table` (nullable, an expand step), then the other five in order inquiries, records (its key `inquiry_id` needs them), links, embeddings, results; the `registry` value of `api_tokens.role` and its two binding columns are added in the same file |
  | 0007 | the rights tables (`roles`, `role_assignments`, `right_requests`, `right_grants`) point to `tasks`, `owners`, `confirmations`, `task_runs`, `registry_inquiries`; `registry_records` gets `right` and `consumed_at` and the kind `permission`; `task_runs` gets the value `chief_engineer` of `role`, `participant` and `role_assignment_id` | all targets exist since 0001 to 0006; `roles` first, then `role_assignments`, `right_requests`, `right_grants`; the `task_runs` columns are nullable (an expand step) and `role_assignment_id` is added by an `alter table` after `role_assignments`; phase 2 (the use by the chief engineer comes in phase 4) |
  | 0008 | `gpu_leases` to `workers.machine_id`, `task_runs.execution_id`, `tasks` | all exist since 0001, 0002, 0004; phase 5 |

  A test applies the migrations one by one to an empty database and checks the schema after each file; it fails when a
  table of this document is in no file or in two (`migration-order`).
- Expand then contract (architecture): a release works with the schema before and after it; a column or value is
  removed one release after nothing reads it. Rolling code back needs no schema rollback. A contracting migration is
  preceded by an automatic backup, and its documented rollback is restore from that backup into a new database.
- A failed migration leaves the previous schema (transaction) and the services unstarted; this is the failure scenario
  "migration error" and its check.
- Backup (spec 18.1): `pg_dump` custom format of the application database, taken with `af_backup`, plus the artifact
  files. Order: artifact files are copied first, then the dump, so every artifact row of the dump has its file (storage
  keys are content-addressed and files are never changed). The Temporal database is dumped separately and restored as a
  pair; the backup records both together with the schema version. A backup is not proof: the restore check loads it into
  a separate environment, runs the migrations to head, checks foreign keys, row counts, artifact checksums, and the
  reconciliation below.
- Reconciliation after a restore (scenario D): a restored database may lag Temporal. Outbox rows that were `done` after
  the backup are unknown, so decisions may be redelivered; this is safe because the Update id is the outbox id and the
  workflow checks `used` from the decision row. `PersistTaskEvent` is idempotent by `(task_id, dedupe_key)`, so the
  workflow replays what the projection lacks. A decision confirmed to an owner after the backup point is lost with it:
  the restore procedure says so and lists the owner's decisions by the Temporal history.
