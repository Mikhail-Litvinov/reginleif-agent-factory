# Recon for rig-owns-actions (step 0, read-only)

Hub = the telegram-hub clone, `plugin/` (paths below relative to it). Nothing was run against live sessions.

## 1. Claude PID

- The in-window module (`src/mod/register.ts`, `commands.ts`) does NOT know the PID. Its Deps have no pid; `/stop` makes the module compact, then POST `/terminate` to the hub (`commands.ts` `stop()`, ~l.258).
- The PID is found by the separate MCP plugin process (`src/plugin/main.ts:98-108`, `terminate`): `findClaudePid(process.ppid, processInfoFor(platform), process.env.CLAUDE_PID)` then `process.kill(pid)`.
- `src/plugin/claude-process.ts:23-37`: use `CLAUDE_PID` if set and it names a claude process, else walk up parents from `from` until a process named `claude`/`claude.exe` or `node` running `…/claude-code/cli.js`. Loop guarded by a visited set.
- Platforms: Windows `windowsProcessInfo` = `powershell Get-CimInstance Win32_Process` (name|parent), 10 s timeout (l.64-69); Linux reads `/proc/<pid>/stat` + `cmdline` (l.43-56). macOS falls into the Linux branch and has no /proc (not supported). Works as written on Win and Linux, but only from a child of claude (the MCP server is a child). No evidence that Claude sets `CLAUDE_PID`; grep shows only this one read of it (main.ts:100).
- The session id comes from env `CLAUDE_CODE_SESSION_ID` (main.ts:51); the module gets it via `$.session.id()`. Hook inputs carry `transcript_path`, `cwd`, `session_id` (types l.872-875); the hub's session-start hook stores the transcript path (`hub/sessions.ts` `transcript`).
- Rig options: (a) module spawns a one-shot child with `$.process.run(["python","-I","-c",…os.getppid()])` / `powershell` and records the parent PID. The module runs inside Claude Code, so the child's parent should be claude. UNTESTED hypothesis; needs a live probe (engine may run modules in a worker or via an intermediary). (b) `rig session` finds the PID by session id from outside: scan processes whose cmdline has `--resume <id>` / matching cwd: unreliable (fresh sessions have no flag). (c) a rig-owned tiny hook (classic `SessionStart` command hook, a child of claude) writes `os.getppid()` / the walk above into `~/.agent-rig/sessions/<id>.json`; needs only hooks, no module, and mirrors the hub's approach. Recommended: (c) for PID, module for the rest.
- To reproduce hub logic rig needs: the process reader per platform (PowerShell CIM on Windows, /proc on Linux), the name regexes, and the ancestor walk. Hub tests live in `test/` (not read).

## 2. Local plugin with a module from the rig manifests

- Manifest field `plugins: string[]` (`src/feature.ts:70`, validated `isStringArray` l.129). Entries are `name@marketplace` (known marketplaces only: `claude-plugins-official`, `openai-codex`, `src/apply.ts:497-501`) or a bare name = the HUB plugin (`apply.ts:450-458`): marketplace name read from `<hubPath>/.claude-plugin/marketplace.json` (`readHubMarketplaceName`, l.476), source = `state.paths.hub`. Base has `"plugins": []` (base/feature.json:435).
- Install mechanics (`src/assets/installer.ts:211-314`): `PluginPlan {enabled,id,marketplace,source}`; `claude plugin marketplace add <source>` if the marketplace is not registered, `claude plugin install <id> --scope user --yes`; a folder registered under a different name is removed first (stale logic); records kept in state for uninstall.
- So a local rig plugin needs no new installer: the installer already takes any folder as `source` with a `.claude-plugin/marketplace.json`. Minimal addition: a third kind of entry resolved against the rig clone, e.g. a bare-name-with-prefix such as `rig:<name>` (or an object `{ "local": "plugins/rig-session" }`), whose plan is `{ id: "<name>@<marketplaceNameFromThatFolder>", marketplace, source: <repo>/plugins/<dir> }` where the folder holds `.claude-plugin/marketplace.json` (relative `source: "./plugin"`, like the hub's). Reuse `readHubMarketplaceName` generalised to a folder; `base` is always enabled (`apply.ts:449`). Also extend `isStringArray` check if the shape changes, and `recordedHubPlans`-style handling for disabling.
- Note: a folder marketplace with a relative-path entry is read from the folder itself, not a copy (reference.md l.124), so edits in the rig clone reach sessions after `/reload-plugins`. Alternative with no marketplace: `~/.claude/skills/<name>` auto-loads as `<name>@skills-dir` (`claude plugin init`), but rig has `skills`/assets handling; not investigated.
- How the hub plugin declares its module: `plugin/.claude-plugin/plugin.json` has only name/version/description/keywords/author (no modules key). The module is declared in `plugin/hooks/hooks.json` as `"modules": ["../src/mod/register.ts"]` (path relative to hooks.json), next to the classic `hooks` (SessionStart/Stop/PreToolUse command hooks, `bun "${CLAUDE_PLUGIN_ROOT}/src/hook/*.ts"`). The MCP server is declared in `plugin/.mcp.json`. Marketplace: `<hubroot>/.claude-plugin/marketplace.json` `{name:"telegram-hub", plugins:[{name:"telegram-hub", source:"./plugin"}]}`. Authoring skill layout for a pure mod: `.claude-plugin/plugin.json`, `hooks/hooks.json` `{ "modules": ["./register.ts"] }`, `hooks/register.ts` exporting `register: Register` from `'claude-code'`. Module has no Node/Bun: file, http, process access only via `$` (`$.fs`, `$.process.run/spawn`, `$.http.fetch`, `$.clock.every`, `$.env.get`). Tools: `claude plugin validate <path>`, `claude plugin test [dir]` (both exist in `claude plugin --help`).
- Concern: the hub's module imports plain TS helpers from `shared/` (commands.ts header says "imports only types and plain helpers that need nothing at run time"), so bundling shared code is fine without a build step.

## 3. Launch command and cswap accounts (/run)

- File `~/.claude/channels/telegram-hub/config.json` (`src/shared/config.ts:15-24` `paths()`, overridable by `TELEGRAM_HUB_STATE_DIR`). Section `launch: { command: string[], timeoutSec (default 90) }` (config.ts:88-135, `launchSchema`, `loadConfig`). Live shape on this machine: `command` = `["cmd.exe","/c","start","","wt.exe","-w","new","-d","{cwd}","cmd.exe","/c","cswap.exe run {account} --share-history -- --channels plugin:telegram-hub@telegram-hub --resume {session} {mode} & exit /b 0"]`, `timeoutSec` 90 (README l.31-52, 408-425 show the same plus a Linux tmux/xterm form).
- Placeholders `{cwd} {account} {session} {mode}` expanded in `src/hub/launch.ts:42-63` `launchCommand` after validation: session = UUID regex; account `^[\w.@-]+$` ("" allowed); mode in `manual|auto|acceptEdits|plan|dontAsk` and the command must contain `{mode}`; on Windows cwd must not contain `"%&|<>^`; cwd must be a directory. A `{mode}` alone expands to `--permission-mode X` as two args. Spawn: `spawnDetached` (launch.ts:~80): detached, stderr to temp file, failure = non-zero exit within 2 s (`LAUNCH_EXIT_GRACE_MS`).
- Accounts are not in config. The set of accounts = "cswap exists" (`hub.ts:3034-3036` `hasAccounts()` = `Bun.which(cswap.exe|cswap)`); an account number is just a number from a session's config dir (`accountOf`, `hub/sessions.ts:48-50`: profile folder `<n>-<email>` under the sessions dir) or from `cswap status` for the default login. Account of a session is stored in `sessions.json` (`SessionRecord.account`). No account list is read from cswap by the hub (no `cswap list` call found).
- The 'mode' of a session is read from the transcript (launch.ts, MODE_BLOCK_BYTES backwards scan; not read in detail).

## 4. /info

(a) Data sources inside the module (`src/mod/commands.ts:132-162`, `execute` "info"; `register.ts`):
- Context: `$.session.usage({breakdown:"summary"})` -> `Usage { context:{tokens?, window, breakdown?:{totalTokens, rawMaxTokens, autoCompactThreshold?, isAutoCompactEnabled}}, rateLimits: RateLimit[] }`; `RateLimit {kind, percentUsed, resetsAt?: ISO string}`.
- Claude limits: own `usage.rateLimits` are replaced by the shared reading when the hub has one (`sharedLimits`: GET `/limits?session=`). Module hook `session.measure` (register.ts:34-37) POSTs `{sessionId, at: now, rateLimits}` to `/limits` (`measured`, commands.ts:~172) when non-empty. Hub (`hub.ts:670-679, 729-738`): `limits` map sessionId -> reading+account; `freshestLimits(sid)` = highest `at` among sessions that are the same session or have the same account (`accountOf(sid) ?? r.account`); with unknown account only the session's own. Account of a session: hello message `configDir` -> `accountOf` (profile folder number), else for the default config dir `cswap status` first line `^Status: Account-(\d+)` (`hub/default-account.ts`, env `PYTHONIOENCODING=utf-8`, CLAUDE_CONFIG_DIR removed, 15 s timeout), stored in the session record.
- For rig: persist per-session `{sessionId, account, at, rateLimits}` files written by the module (`~/.agent-rig/…`) and let `rig info` pick max `at` among files with the same account (+ the session's own). Account must be derived the same way: from the session's config dir (CLAUDE_CONFIG_DIR value, not exposed to hooks? `$.env.get("CLAUDE_CONFIG_DIR")` should work) via `^(\d+)-`, else `cswap status`.
- Both "age" strings: limits older than 300 000 ms (`STALE_LIMITS_MS`) show "(data N old)".

(b) Text (`infoText`, commands.ts:~397-452; strings `shared/i18n/en.ts:186-204`, `ru.ts:175-192`). Output joined by `\n`; blocks separated by one empty line. Markup is Markdown: only the header lines use `**bold**`; everything else plain.
1. Claude: no limits -> `Claude limits: no data, they appear after the model's first reply` (ru `Лимиты Claude: нет данных — появятся после первого ответа модели`); else `**Claude limits**` or `**Claude limits** (data <age> old)` (ru `**Лимиты Claude**` / `(данные <age> назад)`), then one line per limit sorted five_hour, seven_day, others: `<name>: <percent>%` + ` (resets in <dur>)` when resetsAt is in the future (ru `(сброс через <dur>)`). Names: `5 hours`/`Week` (ru `5 часов`/`Неделя`), kind `NNm` -> duration of NN min, else raw kind. Claude percent is not rounded or clamped here (value as given).
2. Codex (only when hub returned a reading or an error object): error -> blank line + `Codex limits: no data, <reason>` (ru `Лимиты Codex: нет данных — <reason>`); ok -> blank + `**Codex limits**[ (data … old)]` + same limit lines but percent `0` when the reset time already passed else `Math.round`.
3. Volunteers (only when result not `none`): ok -> blank + `**Volunteer limits**[ (data … old)]`, `Day: <rounded>% (resets in <dur>)` (or `Day: 0%` when reset passed/unknown; ru `День: …`), then `<Provider>: <used>/<cap>` per provider with a known cap (names OpenRouter/Requesty/Groq/Zhipu; note "Z.ai" avoided because Telegram links domains); error -> blank + `Volunteer limits: no data, <reason>` (ru `Лимиты волонтёров: нет данных — <reason>`).
4. Context: blank + `**Context**` (ru `**Контекст**`), then one line: no data -> `no data`/`нет данных`; if autocompact enabled with threshold: `[≈]<round(used/1000)>/<round(threshold/1000)>k`; else `[≈]<tokens(used)>` (`Nk` or `N.NM`, `shared/tokens.ts`). `≈` when `context.tokens` is missing and the local estimate stands in. `used = context.tokens ?? breakdown.totalTokens`.

## 5. What rig cannot reach without the in-window module

- `$.session.usage()` (context tokens, breakdown, autocompact threshold, own rateLimits) and `session.measure` rate limits exist only inside Claude Code. Without the module: context could be estimated from the transcript (last assistant message `usage` fields) and limits from the statusline/transcript is not confirmed; both are lossy (the `≈` estimate form and the auto-compact threshold are engine values). So `rig info` needs the module to write a snapshot file (usage + limits + account) and read it from there; staleness = file age.
- `$.command.run` (`/rename`, `/autocompact`), `$.session.compact` (and their result `skip`/`tokensBefore`/`tokensAfter`): module only.
- Transcript path/cwd come from hook inputs; PID via a hook child (see 1).

1. PID discovery from inside the module is unproven; a classic command hook (child of claude) is the safe path.

3. The plan's "account block" and "account-allowlist gating" do not match what the hub does today; confirm intent.
4. The `/cleanup` "compact returned success but did not shrink" case was not reproduced (needs a live session).
5. macOS unsupported by the hub's PID code.
