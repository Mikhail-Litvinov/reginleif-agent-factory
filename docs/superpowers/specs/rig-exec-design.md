# Rig exec

`rig exec` runs shell commands independently of the client. The CLI returns one JSON object; failures have the common `{error: {code, message}}` form and exit 1. Command text is UTF-8 on stdin for `start`.

| Command | Success |
| --- | --- |
| `rig exec start <pwsh\|cmd\|bash> --cwd <dir>` | `{id, shell, cwd, pid, startedAt}` |
| `rig exec status <id> [--from <byte offset> [--wait <ms>]]` | `{id, shell, cwd, state, startedAt, end?, log: {from, to, size, text}}`; for a rig run `args` replaces `cwd` and an ended run adds `result?` |
| `rig exec start rig -- <arg…>` | `{id, shell: "rig", pid, startedAt}`; no `cwd` key |
| `rig exec stop <id>` | `{id, stopping: true}` or `{id, state: "ended"}` |
| `rig exec list` | `{runs: [{id, shell, cwd, state, startedAt, end?}]}`, newest first; a rig run shows `shell: "rig"` and `args` instead of `cwd` |

The offset is a nonnegative byte offset; the next poll uses `log.to`. A response reads at most 64 KiB (`EXEC_LOG_CHUNK_BYTES`), so its size stays bounded whatever the log size; the caller polls for the rest. A partial UTF-8 character at a chunk boundary waits for the next poll.

`--wait <ms>` (only after `--from`) makes status a long poll. `<ms>` is a nonnegative integer of decimal digits no larger than `Number.MAX_SAFE_INTEGER`; any other value is `usage`. The call answers at once when the run has ended (including a `lost` end just recorded) or the log holds complete bytes past the offset (`size` past `from`, a partial UTF-8 tail not counting, so the answer is never empty while the caller waits); otherwise it re-checks every `EXEC_WAIT_POLL_MS` (250 ms, from the injected clock) and answers at the latest when `<ms>` has passed. The answer is the same JSON as a plain status, computed at the moment of the answer. A timeout is not an error. Without `--wait` the status is answered at once, as before. The hub polls every 20 to 30 seconds with `--wait`, so output reaches it within the poll interval plus at most one check.

`pwsh` and `cmd` require their respective feature enabled and Windows; `bash` is available on supported platforms.

Each run has a filename-safe id and a directory `~/.agent-rig/exec/<id>/`. `record.json` holds its shell, command, working directory and start time. `identity.json` holds the runner PID and its creation time. `log` holds raw combined stdout and stderr bytes. `heartbeat` holds the last heartbeat timestamp, `exit.json` the end, `stop-request` records a stop in progress (it holds the time of the first request), and `runner-stderr` captures internal runner startup errors. Shell-specific script files also live in the run directory. Files that hold a whole content (scripts, `record.json`, `identity.json`, `result`) are written whole and replace any earlier content; only `log` is appended to. The environment is built in the runner and never stored in a file.

Start writes the log and heartbeat before exclusively creating the initial record and starts the internal `exec-runner` command detached and hidden on Windows. On Windows "detached" also means outside the caller's job object: the hub runs as a Scheduled Task inside a job, and stopping the task (the hub restart of `rig update`) ends that job with every process in it, so a runner left in the job would die with the hub. One mechanism (`spawnDetached` in `src/commands/windows-spawn.ts`) serves every detached start (the runner, a session launch, the hub restart step): it creates the process with `CREATE_BREAKAWAY_FROM_JOB`, and when the caller's job forbids breakaway (a Scheduled Task's job has no limit flags, so it does) a broker started through WMI `Win32_Process.Create` starts the process instead, outside the job. The new process gets the caller's environment without `CLAUDE*`, `TELEGRAM_HUB_*` and `ANTHROPIC_*` names, its own stderr file, and NUL for stdin and stdout. The runner's kill-on-close job is created by the runner itself and nests normally. POSIX is unchanged. The runner records its own identity before building the shell launch, writes its scripts, starts the child, appends both streams to the log, updates the heartbeat and writes the exit once the whole run is over (see Run lifetime). The heartbeat interval is 10 seconds (`EXEC_HEARTBEAT_MS`); a heartbeat at least three intervals old (`EXEC_STALE_MS`) is only stale: the run is `lost` when the runner identity (PID and creation time in `identity.json`) is also missing, unreadable or no longer matches a live process, and then `lost` is written to `exit.json` once, exclusively, by whichever of status, list or stop sees it first. A stale heartbeat with a live runner (machine sleep, a long stall) stays `running`.

An end has `{kind: "exit" | "stopped" | "lost", code: number | null, at, reason?}`. Stop is a request: it checks the PID creation time and the current exit, writes the stop request (a repeated stop never moves the request's time) and answers `{id, stopping: true}`; the runner alone decides and records the end (see Run lifetime), and kills the run's processes itself. A runner that does not act within the grace `EXEC_STOP_GRACE_MS` (five polls: one to see the request, one to see the members gone, the two-second output drain and a poll of slack) is hung, and the next stop kills it from outside, after the identity check: on Windows its process tree (the runner also puts itself in a kill-on-close job object, so descendants that left the parent chain, as Git Bash commands do, die with it), on Linux and macOS its whole process group (so backgrounded descendants that were reparented away die too), and then records `stopped`. A reused PID is never killed (the run ends `lost`). After the kill stop polls the runner by the same identity check (a bounded time on the injected clock) and records `stopped` only once the runner is gone; a failed outside kill means the runner is still alive after the kill (verified by identity), not a non-zero killer exit (a killer that ran counts as ok). A failed outside kill leaves the request in place, writes no end, answers an error and is retried by the next stop. End files are created exclusively, so the first end wins. When the runner cannot write its end, it writes a last-resort end `{kind: "exit", code: 1, reason: "end-write-failed"}`, also exclusively; the runner never throws from this path, and a run whose end cannot be written at all ends `lost` once its runner is gone. Without an identity file (the runner is still starting) stop writes the stop request and returns `{id, stopping: true}` without a kill. The runner checks for the request after writing its identity and before launching the shell, and then records `stopped` without launching anything. A runner that never starts ends `lost` (no identity and a stale heartbeat). Stop of a `lost` run, or of a run whose runner is found gone, kills nothing on Windows (the kill-on-close job ended the descendants with the runner) and on Linux and macOS kills the dead runner's process group while no process holds its PID: a group id of a live group cannot be reused as a PID, so that group is still the old one; if another process holds the PID the old group is gone and nothing is killed. The group may already be empty, so a failed kill there is not an error. Exec does not use the rig apply/update lock. Listing skips invalid or missing records and reports a `lost` end with a reason for an unreadable or invalid end file, and for an unreadable or invalid heartbeat once the runner is gone. Start prunes a directory without a valid record only once its modification time is at least the stale window (three heartbeat intervals, the same window that makes a heartbeat stale) old: a start creates the directory and writes its record within moments, so a younger one may be a concurrent start in progress. It also prunes the oldest ended runs to retain 50 when possible (`EXEC_MAX_RUNS`); running runs are never pruned and may temporarily exceed the limit.

## Run lifetime

A run is one unit of all its processes on every platform: it is `running` while any process of it lives, not only while the command it started lives. The run's processes are the runner's job object on Windows (an active process other than the runner) and the runner's process group on POSIX (a live member other than the runner, zombies excluded; the runner leads its own group because it is spawned detached). When the command exits, the runner remembers its exit code and keeps going: output is still collected from the pipes a background process holds open, the heartbeat keeps going, and the runner polls the run every second (`EXEC_RUN_POLL_MS`, one `ps` start per poll on POSIX, far below the heartbeat interval; not a busy loop). When the last process is gone the runner waits for the output (bounded to two seconds once the run is empty, so a descendant that escaped and still holds a pipe cannot hold the run) and writes the end: `exit` with the command's own code.

The runner alone decides the end, from facts it observes in a fixed order on each poll: the stop request, whether the command has exited, and only once it has, the count of processes left (a command that still runs is itself a member, so it needs no count). The decision:

- the command has exited and no process is left: the run is empty, and the end is `stopped` if this runner killed members because of a request, else `exit` with the command's real code. A request that arrives, or is first seen, after the run emptied changes nothing: nothing was killed, so a stop that finds no live member ends as `exit` and answers `{id, stopping: true}` first;
- a request and a process left: the runner kills the run's processes itself (the job's other members on Windows, the group's other members on POSIX; never itself), every poll until none is left, then records `stopped`. The request is read before the count in every poll, so there is no time comparison and no window between "empty" and "recorded";
- a check that cannot be read (the request file, or the count after the command exited) is never an answer, and in particular never reads as an empty run: it is retried on the next poll. When checks keep failing for the stale window (`EXEC_STALE_MS`, 30 seconds) the runner kills what is left and ends with the command's own code and the reason `run-check-failed`. A request already known is honoured meanwhile.

Stop never decides the end itself, except for a hung or gone runner (see above).

A process that leaves the run by its own choice (`setsid` or a double fork into another group on POSIX, a breakaway from the job on Windows) is outside the run: the run neither waits for it nor kills it.

## Shells

The command text never goes into a quoted template: it is written to a file or passed in an environment variable, and the shell reads it from there. `pwsh` writes the text to `command.user.ps1` and a wrapper to `command.ps1`, both UTF-8 with a BOM so Windows PowerShell reads them as UTF-8, and runs `pwsh -NoLogo -NonInteractive -ExecutionPolicy Bypass -File command.ps1`. The wrapper sets UTF-8 output, parses the user file (parse errors go to stderr, exit 1), inserts an exit-code check after each top-level statement, writes the result to `command.run.ps1` (also with a BOM) and runs it; a native command's nonzero exit code ends the run with that code, and the marker `$global:RigExecDone` tells a script that ran to its end from one that called `exit`. Every shell starts from the full path its check found, never from a bare name that the OS would resolve again. `pwsh` is the first `pwsh` (`pwsh.exe` on Windows) in the parent `PATH`, found by file lookup through the file port with no lookup process; when it is absent on Windows, the executable is Windows PowerShell at `SystemRoot\System32\WindowsPowerShell\v1.0\powershell.exe`. A shell with no executable found is refused with `exec-unavailable` before anything is spawned.

`cmd` takes the text in the environment variable `RIG_EXEC_LINE`, wrapped in double quotes, and runs `cmd.exe /d /v:on /s /c "chcp 65001>nul 2>nul & cmd /s /c !RIG_EXEC_LINE!"` with verbatim arguments, so the text is expanded by delayed expansion and not parsed as part of the outer line; no file is written. Text with a line break is refused with a `usage` error: `cmd` runs one line. The executable is `SystemRoot\System32\cmd.exe`.

`bash` writes `command.sh` as UTF-8 without a BOM, prefixed with `set -eo pipefail`, and runs `bash -l command.sh` (the script path with forward slashes), a login shell, with `CHERE_INVOKING=1` so Git Bash stays in the working directory. On Windows the executable is Git for Windows' `C:\Program Files\Git\bin\bash.exe` (`WINDOWS_BASH` in `src/exec-shell.ts`); elsewhere it is the first `bash` in the parent `PATH`, by its full path.

The environment is built fresh, never copied whole from the runner's parent. On POSIX it is the parent environment. On Windows it starts from the parent's system variables only (`SYSTEM_VARS`: `SystemRoot`, `USERPROFILE`, `APPDATA`, `ProgramFiles` and the like, plus `PROCESSOR_*`), then applies the registry keys read with `reg query`, each with a 10 second timeout (`REG_TIMEOUT_MS` in `src/exec-shell.ts`): machine `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment`, then `HKCU\Volatile Environment`, then user `HKCU\Environment`, so the later key wins. Within a key plain values go first and `REG_EXPAND_SZ` values after them, with `%NAME%` expanded from what is already set. `Path` is not overridden: it is the machine `Path` and the user `Path` joined with `;`. If the machine or the user key cannot be read, the cleaned parent environment is used instead. Both ways drop every variable whose name starts with `CLAUDE`, `TELEGRAM_HUB_` or `ANTHROPIC_` (case-insensitive). `ANTHROPIC_` names carry API keys and endpoints, and `TELEGRAM_HUB_` names carry the hub's bot token and settings: secrets a started process must not see. The same cleaning (one function, `src/clean-environment.ts`) applies to every process rig starts for a client: typed shell commands, the rig kind below, the exec runner itself and the launch of `rig session run`; no variable is kept as an exception, because rig's own code reads none of these prefixes. `CLAUDE` names (`CLAUDECODE`, `CLAUDE_CONFIG_DIR` and the like) would make a `claude` started by the command act as nested in the calling session or run under its account.

## Rig runs

`rig exec start rig -- <arg…>` runs rig's own mutation (`update`, `feature <name> enable|disable`, `language`, any other rig command) detached, so it survives the caller: `rig update` restarts the hub, and a blocking call from the hub would die with it. The arguments are in argv after `--`; nothing is read from stdin and there is no `--cwd`. An empty argument list, and the commands `exec`, `exec-runner` and `update-step`, are refused with `usage` (no recursion, no internal commands); rig validates every other argument itself when the run starts, and its refusal is the run's `result` (`{error: {...}}`) with its exit code.

The record holds `args` (a string array) instead of `cwd` and `text`; validation accepts both kinds. Start returns `{id, shell: "rig", pid, startedAt}` with no `cwd` key. The runner runs `<executablePath> <repo>/src/cli.ts <arg…>` in the rig home directory `~/.agent-rig`. The environment is the runner's own minus the variables dropped under Shells (`CLAUDE*`, `TELEGRAM_HUB_*`, `ANTHROPIC_*`): rig's commands read none of them, and the installers and sessions they start must not inherit the hub's token or API keys. The child's stderr (rig's progress JSON Lines) goes to the run's `log`; its stdout (rig's one JSON object) goes to the file `result` in the run directory.

`status` is as for shells and, once `state` is `ended`, adds `result`: the object parsed from `result` (a success object or `{error: {...}}`). The runner writes `result` whole once the run has ended. It is absent when stdout was empty or not one JSON object; then, for an `exit` end, `end.reason` is `empty-result` or `invalid-result`. `end.code` is rig's exit code. `stop` works as for shells: the run is one kill unit (job object on Windows, process group on POSIX).

Errors use `usage`, `exec-bad-id`, `exec-unknown`, `exec-invalid`, `exec-io`, `exec-unavailable`, or `exec-launch`, alongside errors returned by the shell builder. The internal runner is outside the JSON API. All host access goes through runtime ports.
